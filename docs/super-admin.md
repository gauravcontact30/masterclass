# Super admin monitoring

Open `/dashboard/super-admin`, or choose **Super admin** in the learning dashboard account menu. Both the server page and API verify the current Supabase user and require a confirmed `garvcontact30@gmail.com` email. User-editable role metadata cannot grant access. Both sidebars show hover/focus tooltips when collapsed.

## Deployment

1. Apply `supabase/migrations/0018_super_admin_monitoring.sql` using the Supabase SQL editor or your migration pipeline, before deploying the billing webhook change. The migration adds private monitoring tables, audit triggers and a service-only snapshot RPC. It reads Supabase Auth users, sessions and audit entries through an explicit field allowlist.
2. Keep `SUPABASE_SERVICE_ROLE_KEY` server-only. Existing Supabase and Razorpay environment variables are reused. No new public secret is needed.
3. Enable Razorpay subscription lifecycle, payment captured/failed, refund processed and invoice events for the existing signed webhook URL. Past events are not backfilled automatically. Test subscriptions and signed events in Razorpay test mode before enabling live billing.
4. Sign in with the verified owner account. Verify unauthorized sessions receive 403 from `/api/super-admin` and cannot render the page.

The dashboard refreshes every minute while visible. Reporting windows affect billing, Auth events and request metrics; user counts, subscriptions and content inventory show current state. Tables contain at most 200 recent records each with local search and 20-row pagination. Aggregate totals are calculated in SQL across all matching rows. MRR/ARR are estimates based on configured list prices and active, unexpired subscriptions; captured/refunded payments are grouped by currency and deduplicated by provider entity and event type.

## Coverage and limitations

- Shared `api()` routes record their supplied request path, method, response status and elapsed duration after the response. No query strings, cookies, headers or request bodies are recorded. Non-instrumented Next.js pages/404s and fatal crashes require hosting logs.
- Database triggers record changed column names and record/owner IDs for public application tables present at migration time, excluding monitoring/ledger tables, rate limits and OAuth state. Add the trigger to future tables. Service-role writes do not carry a trustworthy initiating-user identity; they are explicitly marked service/database, with owner IDs where available. Auth role/ban changes record previous/new role and ban expiry.
- Auth logins, IPs and device/session fields come from Supabase Auth. Provider retention and logging determine failed-login coverage. Stored unexpired sessions are not proof of online presence or validity under every session timeout policy.
- Notes and notebook downloads record authenticated owner and generated byte count. Design integrations record provider, operation, status and latency. Credentials and payment secrets are excluded.
- Runtime RSS, process uptime, host memory, CPU count and cumulative CPU time are live process/host observations. CPU percentage, disk capacity, network rates, browser page-load timing, external uptime and automatic downtime notifications require additional hosting telemetry. They are not fabricated.
- The application has no persistent moderation/report/flag backend. The dashboard explicitly reports that this feed is unavailable. It does not introduce account banning, role editing or bulk data exports.
- Configure monitoring retention/archival in your database maintenance pipeline to avoid unbounded event growth. Monitoring writes are best effort, with failures reported to server logs. Audit triggers and billing ledger writes are transactional and require the migration to be present.

## Validation

`node scripts/test-monitoring.mjs` checks SQL migration execution, role isolation, audit events, secret exclusion and payment deduplication with PGlite. Focused Jest tests cover API authorization, billing reconciliation, export behavior and tooltip accessibility. Production migration application and provider telemetry setup require deployment credentials not stored in this repository.
