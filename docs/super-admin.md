# Super admin monitoring

## Trace investigation

Logs, Health, Security and Content include a trace explorer over the latest 200 loaded events in the selected reporting window. Paste an exact request, actor, owner, record or event ID, or select an ID in the timeline to follow related entries. Filter failed responses (HTTP 400+), slow API requests (at least 1,000 ms), or database changes; inspect event details and export the filtered timeline. These relationships are not distributed spans and do not establish causation. Older events outside the snapshot require database or hosting logs.

New responses from the shared `api()` wrapper include a server-generated `X-Request-ID`. Instrumented request events store the same ID in `details.request_id`, and server error logs include it. Caller-supplied IDs are not trusted. Existing events are not backfilled; the existing JSON details column needs no migration. Super admin requests remain excluded from the request event feed.

Activity refresh failures retain the last successful snapshot with a stale-data warning and offer retry when no snapshot exists. Infrastructure configuration checks show unknown status until loaded, expose refresh errors, and disable cache actions until configuration is available. Configuration is not a provider uptime check. Table CSV exports neutralize formula prefixes, and active date filters exclude records with missing or invalid timestamps.

Open `/dashboard/super-admin`, or choose **Super admin** in the learning dashboard account menu. Both the server page and API verify the current Supabase user and require a confirmed `garvcontact30@gmail.com` email. User-editable role metadata cannot grant access. Both sidebars show hover/focus tooltips when collapsed.

## Deployment

1. Apply `supabase/migrations/0018_super_admin_monitoring.sql` using the Supabase SQL editor or your migration pipeline, before deploying the billing webhook change. The migration adds private monitoring tables, audit triggers and a service-only snapshot RPC. It reads Supabase Auth users, sessions and audit entries through an explicit field allowlist.
2. Keep `SUPABASE_SERVICE_ROLE_KEY` server-only. Existing Supabase and Razorpay environment variables are reused. No new public secret is needed.
3. Enable Razorpay subscription lifecycle, payment captured/failed, refund processed and invoice events for the existing signed webhook URL. Past events are not backfilled automatically. Test subscriptions and signed events in Razorpay test mode before enabling live billing.
4. Sign in with the verified owner account. Verify unauthorized sessions receive 403 from `/api/super-admin` and cannot render the page.

The dashboard refreshes every minute while visible. Reporting windows affect billing, Auth events and request metrics; user counts, subscriptions and content inventory show current state. Tables contain at most 200 recent records each with local search and 20-row pagination. Aggregate totals are calculated in SQL across all matching rows. MRR/ARR are estimates based on configured list prices and active, unexpired subscriptions; captured/refunded payments are grouped by currency and deduplicated by provider entity and event type.

## Coverage and limitations

- Shared `api()` routes record their supplied request path, method, response status and elapsed duration after the response. No query strings, cookies, headers or request bodies are recorded. Non-instrumented Next.js pages/404s and fatal crashes require hosting logs.
- Database triggers record changed column names and record/owner IDs for public application tables present at migration time, excluding monitoring/ledger tables, rate limits and OAuth state. Add the trigger to future tables. Service-role writes do not carry a trustworthy initiating-user identity; they are explicitly marked service/database, with owner IDs where available. Auth role/ban changes record previous/new role and ban expiry.
- Auth logins, IPs and device/session fields come from Supabase Auth. Provider retention and logging determine failed-login coverage. Stored unexpired sessions are not proof of online presence or validity under every session timeout policy.
- Notes and notebook downloads record authenticated owner and generated byte count. Design integrations record provider, operation, status and latency. Credentials and payment secrets are excluded.
- Runtime RSS, process uptime, host memory, CPU count and cumulative CPU time are live process/host observations. CPU percentage, disk capacity, network rates, browser page-load timing, external uptime and automatic downtime notifications require additional hosting telemetry. They are not fabricated.
- The application has no persistent moderation/report/flag backend. The dashboard explicitly reports that this feed is unavailable. It does not introduce account banning, role editing or bulk data exports.
- Configure monitoring retention/archival in your database maintenance pipeline to avoid unbounded event growth. Monitoring writes are best effort, with failures reported to server logs. Audit triggers and billing ledger writes are transactional and require the migration to be present.

## Daily busiest hours

User activities includes a date-specific Busiest hours (IST) card. Its date selector is independent of the broader reporting-window selector; Today follows the current Asia/Kolkata calendar date. The card refreshes every 30 seconds while visible and displays the last successful update time.

The protected `/api/super-admin/activity/hours?date=YYYY-MM-DD` endpoint reads non-bot page views within that day's IST boundaries. It returns all 24 hours, daily unique browser and account counts, sessions, and up to five most viewed routes per hour. Selecting an hour reveals its detail. Colors distinguish night, morning, afternoon, and evening. Unique visitor/session counts may overlap between hours and must not be summed into daily totals. If the 20,000-view read cap is reached, the card explicitly labels the report partial. No database migration is required.

For Today, the current IST hour is highlighted with NOW and selected automatically. Follow current hour restores automatic selection after inspecting another hour. The detail panel shows first/latest tracked views, distinct routes, and traffic shares; the current-hour figures are partial through the latest refresh, not live-online counts. Historical dates never show a current-hour marker.

## IP-based visitor location

User activities includes a Visitor locations section with Country, State / region, and City views for the selected 1/7/30/90-day reporting window. It shows unique browsers, page views, sessions, signed-in users, last activity in IST, and location coverage. Counts are deduplicated separately within each location; do not sum cities to get country visitor totals. Search, filters, pagination, and export use the shared admin table.

The protected `/api/super-admin/activity/locations` endpoint reads existing non-bot page-view records, with a 20,000-row limit explicitly marked partial. It returns private, non-cacheable aggregates and requires Super Admin authorization before accessing the database. No migration is needed.

Promotional Tracking has a separate Daily visitor locations table (email, city, region, country, platform, page area, and time), keeping the existing four-column Daily visitor trace intact. Users and activity timelines show region where the underlying record provides it.

Location comes from Vercel's `x-vercel-ip-city`, `x-vercel-ip-country-region`, and `x-vercel-ip-country` request headers already saved by `/api/track`. These describe the public IP location, not GPS, a street address, or verified residence. Region values may be ISO subdivision codes. VPNs, proxies, and mobile networks affect accuracy; local development and older records may have no location. No browser geolocation prompt or external geocoding service was added. Header reference: https://vercel.com/docs/headers/request-headers
